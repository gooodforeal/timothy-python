# timothy-python — стандарт Python-кода

Цель: код, который через полгода откроет незнакомый человек и за минуту поймёт,
**что** делает каждый файл, **зачем** нужна каждая функция и **почему** решение
сделано именно так. Код короткий, быстрый и без лишних сущностей.

## Приоритеты при конфликте правил

1. **Корректность** — код делает ровно то, что нужно, и честно падает на ошибках.
2. **Понятность** — имена, структура, документация.
3. **Простота** — KISS и YAGNI важнее «гибкости на будущее».
4. **Производительность** — правильная сложность алгоритма всегда; микрооптимизации только там, где измерено узкое место.
5. **Краткость** — убираем лишний код, но никогда не за счёт понятности.

Документация (шапка, докстринги, комментарии) **не считается «лишним кодом»** —
правило краткости относится к логике, а не к объяснениям.

Если в существующем проекте уже есть устоявшиеся соглашения (язык докстрингов,
стиль, структура) — следуй им; этот стандарт — дефолт для нового кода и для
мест, где соглашений нет.

## Рабочий процесс

1. **Изучи контекст.** Прочитай соседние модули, найди уже существующие функции,
   модели и утилиты — переиспользуй их вместо написания дублей (DRY).
2. **Спроектируй минимально.** Определи, какие файлы и сущности действительно
   нужны для задачи. Ничего «на вырост».
3. **Напиши код** по правилам ниже: шапка файла → импорты → константы →
   типы/модели → функции/классы → точка входа.
4. **Пройди чек-лист** в конце этого файла.
5. **Проверь запуском и инструментами.** Запусти код на примере данных. Если в
   проекте настроены `ruff`, `mypy`/`pyright`, `pytest` — прогони их. Если не
   настроены — не создавай для них конфиги в проекте пользователя; быструю
   проверку можно сделать временно (`uvx ruff check файл.py`). Эталонный конфиг —
   в `references/project-structure.md`.

## Работа с существующим кодом

Стандарт применяется **к тому коду, который ты пишешь или меняешь в рамках
задачи**, а не ко всему файлу. Задача «поправь баг» не становится задачей
«перепиши модуль».

- **Минимальный дифф.** Меняй только то, что нужно для задачи. Не
  переформатируй, не переименовывай и не документируй чужой код вокруг правки —
  такой дифф невозможно ревьюить, и в нём теряется суть изменения.
- **Новый и изменённый код — по стандарту полностью:** новая функция получает
  докстринг, типы и комментарии; у изменённой функции докстринг и типы
  приводятся в соответствие с её новым поведением.
- **Согласованность с файлом.** Если файл написан в другом стиле (другой язык
  докстрингов, другой формат) — новый код пишется в стиле файла, а не
  стандарта, чтобы файл не превращался в лоскутное одеяло.
- **Замечания — словами, не правками.** Если код вокруг сильно расходится со
  стандартом (нет типов, O(n²), `except: pass`, секреты в коде) — коротко
  перечисли это в ответе и предложи отдельный рефакторинг. Сам рефакторинг —
  только по просьбе пользователя.
- **Исключение:** если правка без исправления соседнего кода невозможна или
  небезопасна (например, функция, которую ты меняешь, глотает исключения, и из-за
  этого фикс не будет работать) — исправь минимально и скажи об этом.
- **Явная просьба «отрефактори / приведи к стандарту»** снимает ограничения:
  тогда применяй весь стандарт к указанному коду, сохраняя поведение. Сравни
  вывод до и после на одних и тех же входных данных (внешние вызовы — подменой во
  временной проверке); тесты в проект — по правилам раздела 11.

## 1. DRY · KISS · SOLID · YAGNI

**DRY — одно знание в одном месте.**
- Повторяющаяся логика (2+ места с одинаковым смыслом) выносится в функцию,
  константу или общий модуль.
- Дублируются не только строки кода, но и «знания»: магические числа, URL,
  форматы дат, SQL-фрагменты, тексты ошибок → константы/конфиг.
- Не путай похожий код с одинаковым смыслом: если два куска совпадают случайно и
  будут меняться независимо — не склеивай их.

**KISS — самое простое решение, которое работает.**
- Функция вместо класса, если нет состояния. Словарь/`dataclass` вместо иерархии.
- Стандартная библиотека раньше самописного кода, проверенная библиотека раньше
  своего велосипеда.
- Без метапрограммирования, хитрых декораторов и магии, если задача решается
  прямолинейно.

**SOLID — по-питоновски, без Java-церемоний.**
- **S** — модуль/класс/функция отвечает за одну вещь. Признак нарушения: в
  названии нужно «и» (`load_and_validate_and_save`).
- **O** — расширяем добавлением кода (новая стратегия, новый обработчик в
  словаре-реестре), а не правкой длинных `if/elif` по всему проекту.
- **L** — наследник работает везде, где работает родитель; не переопределяй
  методы так, чтобы они кидали `NotImplementedError` «потому что не подходит».
- **I** — маленькие интерфейсы. В Python — `typing.Protocol` с 1–3 методами.
- **D** — бизнес-логика получает зависимости (клиент, репозиторий, сессию)
  аргументами, а не создаёт их внутри. Это делает код тестируемым.

**YAGNI — см. раздел 2.**

## 2. Никакого кода «про запас»

Пишем только то, что нужно для текущей задачи.

**Запрещено:**
- Абстрактный базовый класс / `Protocol` с единственной реализацией и без тестовых
  подмен.
- Фабрики, менеджеры, билдеры, реестры «на будущее».
- Класс, у которого только `__init__` и один метод — это функция.
- Обёртки над стандартной библиотекой, которые ничего не добавляют
  (`def read_file(path): return open(path).read()`).
- Параметры, флаги и настройки, которые никто не передаёт.
- Закомментированный старый код, неиспользуемые импорты, функции и переменные.
- Универсальные `utils.py`/`helpers.py`-свалки с функциями «вдруг пригодится».

**Разрешено и правильно:**
- Вынести функцию, вызываемую один раз, **если** она именует законченный шаг
  алгоритма и делает родительскую функцию заметно читаемее (например, длинную
  функцию на 80 строк разбить на 3 шага по смыслу). Это про ясность, не про
  переиспользование.
- Абстракцию — когда уже есть **вторая** реализация или тест требует подмены.
  Правило трёх: на третьем повторе обобщаем обязательно.

## 3. Именование

Имя должно отвечать на вопрос «что это / что делает» без чтения тела.

| Сущность | Стиль | Правило | Пример |
|---|---|---|---|
| Модуль, пакет | `snake_case` | существительное по области | `payment_gateway.py` |
| Класс | `PascalCase` | существительное | `InvoiceRepository` |
| Исключение | `PascalCase` + `Error` | что пошло не так | `PaymentDeclinedError` |
| Функция, метод | `snake_case` | глагол + объект | `calculate_total_price()` |
| Булево | `snake_case` | `is_` / `has_` / `can_` / `should_` | `is_expired`, `has_access` |
| Константа | `UPPER_SNAKE` | на уровне модуля | `MAX_RETRY_ATTEMPTS` |
| Коллекция | множественное число | `<значение>_by_<ключ>` для словарей | `users`, `user_by_id` |
| Приватное | `_prefix` | не часть публичного API модуля/класса | `_parse_row()` |

**Правила:**
- Единицы измерения — в имени: `timeout_seconds`, `file_size_bytes`, `price_rub`.
- Без сокращений, кроме общепринятых: `id`, `url`, `db`, `api`, `http`, `config`.
- Запрещённые «пустые» имена: `data`, `info`, `obj`, `item`, `tmp`, `res`, `val`,
  `manager`, `helper`, `process()`, `handle()`, `do_stuff()`, `x` (кроме математики
  и коротких лямбд/comprehension с очевидным смыслом).
- Функция, которая возвращает значение, называется по результату или действию
  (`get_active_users`, `build_report`); функция-предикат — как вопрос
  (`is_valid_email`).
- Одно понятие — одно слово во всём проекте: не смешивай `fetch`/`get`/`load`/`retrieve`
  для одного и того же действия.

Пример «до → после»: `references/examples.md`, раздел «Мини-примеры».

## 4. Документация: шапка, докстринги, комментарии

Язык документации — **русский** (если в проекте не принят другой). Имена в коде —
всегда английские. Подробные шаблоны для всех случаев: `references/documentation.md`.

### 4.1. Шапка файла — обязательна в каждом `.py`

Модульный докстринг в самом начале файла (до импортов). Первая строка — резюме
с точкой, затем секции: **«Назначение»** (что делает модуль и зачем нужен —
обязательно), по смыслу — «Основные компоненты», «Пример», «Запуск»,
«Переменные окружения». Для `__init__.py` — короткая шапка пакета, для тестов —
что именно тестирует файл. Шаблоны: `references/documentation.md`, раздел 1.

### 4.2. Докстринги — на каждый класс, функцию и метод

По PEP 257 в Google style. Включая приватные методы и `__init__`.

- Первая строка — краткое описание действия в изъявительном наклонении,
  с точкой: «Загружает…», «Возвращает…», «Проверяет…».
- Затем пустая строка и подробности, если они нужны: поведение, побочные эффекты,
  граничные случаи.
- Секции `Args:`, `Returns:` / `Yields:`, `Raises:` — когда есть что в них написать.
  Типы **не дублируем** — они в аннотациях.
- Для тривиальных методов (`__repr__`, простые property) достаточно одной строки.

Шаблоны для функции, класса, dataclass, генератора, async, property, исключения,
Protocol, Enum: `references/documentation.md`, раздел 2.

### 4.3. Inline-комментарии — везде, где есть логика

Каждый логический блок функции предваряется коротким комментарием, объясняющим
**намерение** шага. Комментарий говорит «зачем» и «что по смыслу», а не
пересказывает синтаксис.

**Обязательно комментируем:**
- каждый смысловой шаг в функции длиннее нескольких строк;
- неочевидные условия, регулярные выражения, формулы, битовые операции;
- магические значения, которые нельзя вынести в константу с говорящим именем;
- обходы багов, ограничения внешних API, причины «странных» решений;
- выбор алгоритма/структуры данных по соображениям производительности.

**Запрещено:**
- тавтология: `count += 1  # увеличиваем count на 1`;
- устаревшие комментарии, не соответствующие коду;
- закомментированный код (для истории есть git).

Примеры хороших и плохих комментариев: `references/documentation.md`, раздел 3.

## 5. Производительность

Сначала правильный алгоритм и структура данных, потом всё остальное.
Детальные паттерны с примерами «до/после»: `references/performance.md`.

- **Структуры данных:** проверка вхождения — `set`/`dict` (O(1)), не `list` (O(n)).
  Очереди — `collections.deque`. Подсчёт — `Counter`. Группировка — `defaultdict(list)`.
- **Без O(n²) там, где есть O(n):** вложенный цикл поиска заменяем на словарь-индекс.
- **Большие данные — потоком:** генераторы, построчное чтение файлов, `itertools`,
  чанки при работе с БД. Не грузи всё в память без необходимости.
- **Строки:** `"".join(parts)` вместо `+=` в цикле; f-строки для форматирования.
- **Не повторяй дорогую работу:** выноси инварианты из циклов, компилируй regex
  один раз на уровне модуля, кэшируй чистые функции через `functools.cache`/`lru_cache`.
- **I/O:** батчи вместо запросов по одному, избегай N+1 к БД, переиспользуй
  HTTP-сессию/клиент, всегда ставь таймауты.
- **Конкурентность:** I/O-bound — `asyncio` или `ThreadPoolExecutor`;
  CPU-bound — `ProcessPoolExecutor` или векторизация (`numpy`/`pandas`/`polars`).
- **pandas/numpy:** векторные операции, никаких `iterrows()`/`apply` по строкам,
  если есть векторный аналог.
- **Измеряй, а не угадывай:** `cProfile`, `timeit`, `py-spy`. Микрооптимизации,
  ухудшающие читаемость, — только для доказанного узкого места и с комментарием,
  почему так.

## 6. Структура файлов и папок

Код разбит по смыслу так, чтобы по дереву папок было понятно устройство
проекта. Шаблоны структур и `pyproject.toml`: `references/project-structure.md`.

**Масштаб структуры — по размеру задачи, а не по максимуму.** Каждый лишний
файл и слой — это то, что читателю надо открыть, чтобы понять код. Поэтому
структура растёт вместе с кодом, а не создаётся заранее:

| Размер задачи | Структура |
|---|---|
| Скрипт, утилита, отчёт (до ~300 строк) | **Один файл.** Тесты и доп. модули — только по правилам раздела 11 / при реальной необходимости |
| Маленький сервис или бот (одна-две сущности, ~5 эндпоинтов/команд) | **Плоский пакет из 3–5 модулей**: `main.py` (приложение и роуты), `db.py` или `repository.py` (работа с БД), `schemas.py`, при необходимости `config.py`. Без `src/`, без пустых `services/`/`exceptions.py`, если в них нечего положить |
| Сервис с несколькими сущностями и бизнес-логикой | Слои по шаблону из `references/project-structure.md` |
| Библиотека / пакет для публикации | `src/`-layout, `pyproject.toml` |

- **Ориентир для маленьких задач:** решение со стандартом должно быть сопоставимо
  по объёму с решением без него — разница в документации и типах, а не в
  количестве файлов.
- **Инфраструктурные файлы** (`pyproject.toml`, `.gitignore`, `.env.example`,
  `Dockerfile`, CI) создаются, только если о них просили или без них проект не
  запустится. Для маленького сервиса достаточно `requirements.txt` и команды
  запуска в ответе.
- Не выноси функцию в отдельный модуль, пока у модуля нет своей темы и хотя бы
  нескольких функций.

**Базовые правила:**
- Одиночный скрипт — один файл; `src/`-layout — для библиотек и крупных сервисов.
- Слои — `config.py`, `schemas/`, `services/`, `repositories/`/`clients/`,
  тонкие `api/`/`cli/`/`bot/`, `exceptions.py` — вводятся, когда для них есть код.
  Что кладётся в каждый слой: `references/project-structure.md`, раздел 2.
- Один модуль — одна область ответственности. Имя файла говорит, что внутри.
- Ориентиры размеров: функция ≤ ~40 строк, модуль ≤ ~400 строк, вложенность
  ≤ 3 уровней. Превышение — сигнал разбить по смыслу.
- `__init__.py` — шапка и, при необходимости, реэкспорт публичного API. Без логики.
- `utils.py` допустим только для действительно общих мелких функций, используемых
  в нескольких модулях. Если в нём появляется тема — выноси её в отдельный модуль.
- Тесты зеркалят структуру кода: `src/app/services/billing.py` →
  `tests/services/test_billing.py`.

**Порядок внутри модуля:**
1. Шапка-докстринг.
2. Импорты: стандартная библиотека → сторонние → свои (абсолютные), группы
   через пустую строку, без `import *`.
3. Константы модуля.
4. Модели / типы / исключения модуля.
5. Публичные функции и классы, затем приватные помощники (или помощник рядом
   с единственным местом использования — выбери один подход в проекте).
6. `def main()` + `if __name__ == "__main__": main()` — для исполняемых файлов.

## 7. Краткость без потери ясности

- **Ранний выход** (guard clauses) вместо глубокой вложенности `if`.
- **Comprehension** для простых преобразований; цикл — если внутри больше одного
  условия или есть побочные эффекты. Вложенный comprehension — максимум 2 уровня.
- `any()` / `all()` / `sum()` / `max(..., key=)` вместо ручных циклов-аккумуляторов.
- Распаковка: `first, *rest = items`, `for key, value in mapping.items()`.
- `enumerate` вместо `range(len(...))`, `zip(..., strict=True)` для параллельных списков.
- `dataclass(frozen=True, slots=True)` вместо ручного класса с `__init__`/`__eq__`/`__repr__`.
- `pathlib.Path` вместо `os.path`, `with` для любых ресурсов.
- `match` для разбора структур и множества вариантов одного значения.
- Словарь-диспетчер вместо длинной цепочки `if/elif` по строковому ключу.
- Не пиши то, что делает язык/библиотека: `dict.get(key, default)`,
  `dict.setdefault`, `str.removeprefix`, `itertools.batched`, `functools.partial`.
- Однострочник, который нужно разгадывать, — хуже трёх понятных строк.

Примеры «до → после»: `references/examples.md`, раздел «Мини-примеры».

## 8. Типизация — обязательна всегда

Аннотации типов — такая же обязательная часть кода, как докстринги. Код без
типов не сдаётся. Подробности и примеры: `references/typing.md`.

**Что аннотируем:**
- **Все** параметры и возвращаемые значения каждой функции и метода, включая
  приватные, вложенные функции, `__init__` (`-> None`) и тесты (`-> None`).
- Атрибуты классов и dataclass-полей, константы модуля (`Final` — для того, что
  нельзя переопределять).
- Локальные переменные — только там, где тип не выводится сам: пустые коллекции
  (`seen_ids: set[str] = set()`), переменная, начатая с `None`.

**Как аннотируем:**
- Современный синтаксис: `list[int]`, `dict[str, User]`, `X | None` (не
  `Optional`, не `List`), обобщения PEP 695: `def first[T](items: Sequence[T]) -> T`,
  алиасы `type UserId = int`.
- **Вход — абстрактный, выход — конкретный:** принимаем `Iterable`, `Sequence`,
  `Mapping` из `collections.abc`, возвращаем `list`, `dict`, `tuple`.
- **Никакого `Any`.** Неизвестные внешние данные — `object` с проверкой или
  валидация в модель (pydantic / `TypedDict`). `Any` допустим только на границе с
  нетипизированной библиотекой — с комментарием, почему.
- **Структура вместо безымянных словарей:** `dict[str, Any]` для объекта с
  известными полями → `dataclass`, pydantic-модель или `TypedDict`.
- Фиксированный набор значений — `Literal["csv", "json"]` или `StrEnum`.
- Идентификаторы разных сущностей, которые легко перепутать — `NewType`
  (`UserId`, `OrderId`).
- Зависимости по поведению — `Protocol`; функции-параметры — `Callable[[Order], bool]`.
- `X | None` обрабатываем явно до использования (guard clause), а не надеемся.
- `cast()` — только после реальной проверки; `# type: ignore` — только с кодом
  ошибки и причиной: `# type: ignore[import-untyped]  # у библиотеки нет стабов`.
- Код проходит `mypy --strict` (или `pyright` в strict-режиме).

## 9. Ошибки и логирование

Подробно: `references/errors-and-logging.md`.

- **Ловим конкретные исключения** — никаких голых `except:` и
  `except Exception: pass`. Пустой `except` допустим только с комментарием, почему
  ошибку безопасно игнорировать.
- **Ловим там, где можем что-то сделать:** повторить, подставить значение по
  умолчанию, перевести в понятную ошибку. Не оборачивай каждую функцию в
  `try/except` — пусть исключение долетит до границы (обработчик API, `main()`
  CLI, обработчик бота), где оно логируется и превращается в ответ пользователю.
- **Иерархия исключений:** одно базовое `<App>Error` на приложение и небольшое
  число наследников по смыслу (`NotFoundError`, `ValidationError`,
  `ExternalServiceError`). Не создавай исключение на каждую функцию.
- **Причина сохраняется:** `raise ExternalServiceError("...") from error`.
- **Сообщение с контекстом:** что не получилось, с каким значением, почему —
  `f"Заказ {order_id} не найден"`, а не `"Ошибка"`.
- **Валидация на границе** (API, CLI, файл, очередь) — внутри доверяем типам и не
  проверяем одно и то же повторно.
- **Логирование:** `logger = logging.getLogger(__name__)` в каждом модуле,
  настройка логирования — один раз в точке входа. `print` — только как вывод CLI.
- **Уровни:** `debug` — детали для отладки; `info` — значимые события
  (запуск, итог операции); `warning` — нештатно, но работа продолжается;
  `error` — операция не выполнена; `logger.exception(...)` внутри `except` — чтобы
  записать трейсбек.
- **Ленивое форматирование:** `logger.info("Загружено %d заказов", count)`, не f-строки.
- **Не логируем** пароли, токены, полные номера карт и персональные данные.
- Ошибку либо логируем, либо пробрасываем — не то и другое сразу (иначе один
  сбой даёт несколько одинаковых записей в логе).

## 10. Безопасность

Подробно: `references/security.md`.

- **Секреты** — только из окружения / секрет-хранилища через `config.py`;
  в коде, логах, исключениях и git их нет. `.env` — в `.gitignore`, рядом
  `.env.example` без значений.
- **SQL** — только параметризованные запросы или ORM. Никаких f-строк и
  конкатенации со значениями пользователя.
- **Команды ОС:** `subprocess.run([...], check=True)` списком аргументов, без
  `shell=True` и без `os.system`.
- **Недоверенные данные** никогда не попадают в `eval`/`exec`, `pickle.loads`,
  `yaml.load` (только `yaml.safe_load`), `marshal`.
- **Пути от пользователя** — нормализуем через `Path.resolve()` и проверяем, что
  путь внутри разрешённой папки (`is_relative_to`), иначе — path traversal.
- **Случайность для безопасности** (токены, пароли, коды) — модуль `secrets`, не `random`.
- **Сравнение секретов** — `hmac.compare_digest`. Пароли — только хэш
  (`argon2`/`bcrypt`), никогда не храним и не шифруем «обратимо».
- **Внешний ввод валидируется** по схеме (pydantic) с ограничениями длины и
  диапазонов; размеры загружаемых файлов и запросов ограничены.
- **Сеть:** таймауты всегда, проверка TLS не отключается (`verify=False` — нет).
- **Зависимости** — зафиксированы lock-файлом (`uv.lock`), проверяются `pip-audit`.

## 11. Тесты

Подробно: `references/testing.md`.

**Когда писать тесты.** Тестовый файл — это новый код в проекте пользователя,
который ему придётся поддерживать, поэтому он появляется не по умолчанию:

- **Пишем тесты**, если пользователь их попросил **или** в проекте уже есть
  тесты (`tests/`, `test_*.py`, pytest в зависимостях). Во втором случае новые
  тесты кладём в существующий набор, в его стиле.
- **Не создаём тестовые файлы**, если тестов в проекте нет и о них не просили —
  даже для багфикса. Вместо этого проверяем код сами: запускаем скрипт на
  примере данных или пишем одноразовую проверку во временной папке (scratchpad /
  `tempfile`) и удаляем её. В ответе одной строкой предлагаем добавить тесты.
- Так дифф остаётся тем, о чём просили, а проверка всё равно выполнена.

Когда тесты пишем: `pytest`, тесты зеркалят структуру кода; покрываем
бизнес-логику, граничные случаи, ветки ошибок и исправленные баги; структура
Arrange → Act → Assert; имя описывает сценарий
(`test_calculate_discount_rate_returns_zero_for_inactive_user`); `parametrize` и
фикстуры вместо копипасты; моки только на границах (сеть, БД, время, файлы);
тесты детерминированы и проверяют поведение, а не реализацию. Подробно и с
примерами: `references/testing.md`.

## 12. Прочий технический базис

- **Версия:** Python 3.12+ (или версия проекта). Используй современный синтаксис.
- **Конфигурация** — один `config.py` (например, `pydantic-settings`), единственное
  место чтения переменных окружения.
- **Магические числа и строки** → именованные константы или `Enum`/`StrEnum`.
- **Изменяемые значения по умолчанию запрещены:** `def f(items: list[str] | None = None)`.
- **Ключевые аргументы:** булевы флаги и опции — после `*`, чтобы вызов читался:
  `export(report, *, include_header=True)`.
- **Глобальное изменяемое состояние** — нет. Зависимости передаются явно.
- **Ресурсы** (файлы, соединения, блокировки) — через `with`.
- **Асинхронный код:** никаких блокирующих вызовов внутри `async def`;
  параллельные задачи — `asyncio.TaskGroup`, ограничение параллелизма — `Semaphore`.
- **Инструменты:** `ruff` (линтер + форматтер, длина строки 100), `mypy --strict`
  или `pyright`, `pytest`. Зависимости — `uv` (или то, что принято в проекте).

## Чек-лист перед сдачей кода

Пройди по каждому пункту. Если пункт нарушен — исправь до ответа пользователю.

**Объём правки**
- [ ] Изменено только то, что нужно для задачи; чужой код вокруг не переписан.
- [ ] Замечания по соседнему коду перечислены в ответе, а не исправлены молча.

**Структура**
- [ ] Структура по размеру задачи: скрипт — один файл, маленький сервис — 3–5 модулей без `src/`.
- [ ] Нет непрошеных инфраструктурных файлов (`pyproject.toml`, `.gitignore`, `.env.example`, `Dockerfile`).
- [ ] Каждый файл лежит в логичном месте и назван по содержимому.
- [ ] Нет «свалок» и модулей со смешанной ответственностью.
- [ ] Точки входа тонкие, логика — в сервисах, I/O — в клиентах/репозиториях.

**Документация**
- [ ] В начале каждого нового `.py` есть шапка: назначение, основные компоненты, пример (где уместно).
- [ ] У каждого нового/изменённого класса, функции и метода есть докстринг PEP 257 (Google style).
- [ ] Каждый смысловой блок логики снабжён понятным комментарием «зачем»; нет тавтологий.

**Типы**
- [ ] Все параметры и возвращаемые значения аннотированы, включая `-> None`.
- [ ] Нет `Any` без причины и `dict[str, Any]` вместо модели.
- [ ] Вход — абстрактные типы, выход — конкретные; `None` обработан явно.
- [ ] Тайпчекер в strict-режиме проходит.

**Простота**
- [ ] Нет абстракций, классов, функций, параметров «про запас».
- [ ] Нет дублирования логики и «знаний» (магических чисел, строк).
- [ ] Нет мёртвого и закомментированного кода, неиспользуемых импортов.

**Имена**
- [ ] Имена отвечают на «что это/что делает» без чтения тела; нет `data`, `tmp`, `res`, `manager`.
- [ ] Булевы — `is_/has_/can_/should_`; единицы измерения в имени, где они есть.

**Ошибки и логи**
- [ ] Исключения конкретные, с контекстом и `from error`; нет `except: pass`.
- [ ] Ошибки обрабатываются на границе, а не в каждой функции.
- [ ] Используется `logging` с правильными уровнями; секреты и ПДн не логируются.

**Безопасность**
- [ ] Нет секретов в коде; SQL параметризован; нет `shell=True`, `eval`, `pickle` на внешних данных.
- [ ] Внешний ввод валидируется; пути от пользователя проверены.

**Производительность**
- [ ] Правильные структуры данных, нет лишних O(n²), большие данные — потоком.
- [ ] Нет N+1 запросов; ресурсы через `with`; у сетевых вызовов есть таймауты.

**Тесты и проверки**
- [ ] Код проверен запуском (на примере данных или одноразовой проверкой во временной папке).
- [ ] Тестовые файлы добавлены, только если их просили или в проекте уже есть тесты;
      иначе добавить тесты предложено в ответе.
